# P3-3 — TranslatorFactory has no schema validation for the driver config array …

## Finding / 问题

- EN: TranslatorFactory has no schema validation for the driver config array — a misspelled key or wrong type is silently ignored or produces a confusing error downstream.
- 中文: TranslatorFactory 对驱动配置数组没有 schema 校验——拼写错误的键或错误的类型会被静默忽略，或在下游产生令人困惑的错误。
- Where / 位置: `src/TranslatorFactory.php`
- Verification / 验证: static / 仅静态推断

  second half reproduces, but landing it is a public-behaviour change, so the decision is the user's.

  *Half one — "wrong type … confusing error downstream" — is stale.* Re-checked against the current code:
  every typed key is validated up front by `stringOption()` (`src/TranslatorFactory.php:77-88`, applied at
  `:57`, `:97`, `:106`, `:131-134`) and `translations` by an explicit `is_array` guard (`:111-113`). Probe
  (cwd `/tmp`, the module's own `vendor/autoload.php`, PHP 8.5.10): `file => []`, `locale => 42`,
  `codeset => []`, `driver => 1` and `translations => 'not an array'` each throw
  `InvalidArgumentException: Translator config "…" must be …` — the misleading `file not found: Array`
  the finding describes cannot occur. Pinned by `tests/TranslatorFactoryTest.php:68-77`, `:91-100`,
  `:102-110`, `:112-121`. It landed in `fe38e96` (2026-09-27), one day before this item was filed — the
  report read a state that had already moved.

  *Half two — "a misspelled key is silently ignored" — reproduces.* Probe:
  `create(['driver' => 'array', 'translation' => ['HELLO' => 'Hi']])` returns an `ArrayTranslator` and
  `translate('HELLO')` returns `'HELLO'`; a `defaultDomain` typo (`defaulDomain`) and any unrelated extra
  key are ignored the same way. No warning, no exception.

  *Why `question` and not a fix in this pass.* Rejecting unknown/misspelled keys is the only way to close
  half two, and it changes the public behaviour of `TranslatorFactory::create()`: a config array carrying
  an extra key — e.g. one assembled by merging a defaults array with a caller's config — works today and
  would start throwing. Per the module-owner lane ("a fix forks on something only the user decides: a
  public API, a behaviour, a breaking change") that is the user's call, so I have not chosen it.

  *The decision:* should `TranslatorFactory::create()` reject the config keys it does not read? If yes,
  the change I would land is the one this workspace already uses for the same problem —
  `MiGears\Security\MiAuth::assertKnownOptionKeys()` (`migears-security/src/MiAuth.php:192-206`), which
  rejects misspelled option keys instead of silently falling back to defaults — scoped per driver (array:
  `translations`, `file`; gettext: `locale`, `domain`, `codeset`, `directory`; both: `driver`,
  `defaultDomain`), with a regression test per driver and one line in both README halves. If no, this item
  is a `rejected` on the design decision and I will record it as such. Nothing else in the module blocks it.

  *Re-grade, stated and not applied:* the surviving half is a silent wrong result, which is P2 on the shared
  rubric rather than P3; the front-matter `level` is the tooling's field, so it stays as filed.
